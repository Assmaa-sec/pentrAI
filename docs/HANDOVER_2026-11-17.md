## 2. Architecture and execution path

```text
Dashboard :5173
  -> Vite /v1 proxy -> control plane :8765
       -> identity, organization access, scope authorization
       -> ZIP upload, immutable source digest, recorded execution backend
       -> model selection and credit reservation
       -> authorized assessment in the database
            -> matching worker claims it
            -> signed grant + runner lease + job scope
            -> verified source staging and analysis
            -> evidence-bound findings and report
            -> cleanup and credit settlement
       <- scan details/progress, activity stream, findings, report downloads
```

The dashboard has three recorded backends:

| Backend | Execution path |
| --- | --- |
| `local_static` | `control_plane.local_worker` → `local_static_run` → `static_worker`. Source/dependency analysis without executing the uploaded application. |
| `hexstrike_local` | `control_plane.local_hexstrike_worker` → one networkless assessment container → runner-local HexStrike server/MCP bridge and native analysis loop. |
| `hexstrike` | Separate cluster admission/dispatch path using grants, isolated workloads, leases, and the authenticated result collector. |

Changing configuration does not convert existing assessments to another backend.
Create a new assessment for a newly selected backend rather than rewriting
historical records.

For the native local path, the provider client and credentials stay in the host
worker. Model requests/responses cross the container's stdio protocol. The
container receives job scope and source bytes, not the provider key or database
signing key. It has its own private tool server/MCP bridge; the separately started
host tool server is not the queue worker.

The control plane persists policy and results; it does not execute uploaded code
or run legacy security commands. Completion still requires cleanup confirmation.
A saved report during finalization does not mean cleanup has completed.

The older `python -m pentrai_pipeline` CLI is a separate workflow. Some of its
stages remain unimplemented; a failed Job can still accompany exit code 0 and zero
printed findings. That was identified, not changed, and must not be used to judge
the dashboard's assessment path.

### Original failure and correction

Model selection/key loading happened before execution admission. A setup exception
could be printed while the scan stayed `AUTHORIZED`; polling then selected that
same oldest assessment again, preventing useful queue progression.

`fail_before_execution` now persists a safe failure, records an audit reason,
and releases reserved credits. It acts only on an `AUTHORIZED`,
`hexstrike_local` assessment in the requested organization. It cannot overwrite
another tenant's assessment, a claimed job, or a terminal state. Subsequent polling
can select the next assessment. Repeated handling does not release credits twice.

### Failure reasons covered

Fixed codes cover admission, database access, configuration, missing credentials,
changed model/rates, unavailable execution environment, unreadable/mismatched
source, archive preparation, tool startup, provider authentication/access,
provider quota/rate limits, provider timeout/invalid responses, credit/usage limits,
job deadlines, runner/protocol failure, and rejected or unsaved results.

Raw exceptions, source text, host paths, endpoints, and keys are not copied into
customer diagnostic events. Technical reason codes remain in tenant-scoped audit
records; customer-safe wording is applied at the API boundary.

### Liveness and resource handling

- Dependency checks precede publishing readiness. Global worker readiness and
  per-job `RunnerLease.heartbeat_at` are separate signals; active work refreshes
  both as appropriate. A heartbeat confirms liveness, not analysis progress.
- Stage notices identify source preparation, tool startup, analysis/model waits,
  and result persistence. Periodic wait notices avoid unexplained silence.
- Source reads are bounded by the finalized artifact size and checked against its
  immutable digest. `_write_all` handles partial raw pipe writes.
- Status/error messages use fixed allowlists. Unknown or oversized messages fail
  the protocol; existing `PENTRAI_MODEL`, `PENTRAI_TURN`, and `PENTRAI_RESULT`
  exchanges remain supported.
- Already-expired jobs cannot launch. A watchdog bounds pipe waits and model-call
  waits; cancellation can release a wait even when a provider call is returning
  in a daemon thread. Sub-second deadlines retain their actual remaining time.
- A late successful provider response still goes through the usage ledger after
  cancellation/credit release. Its result cannot complete a cancelled or expired
  assessment. Preserve late-usage accounting when refactoring this path.
- Failed cleanup retains its lease and visible warning. Completion cannot be
  manufactured by discarding resource ownership or marking cleanup successful.
- A claimed native local job is not automatically resumed after worker loss.
  Leases normally last about 15 minutes; restarted maintenance can clean/fail an
  abandoned job at expiry, with progress uncertainty visible during the wait.

`python -m control_plane.local_hexstrike_worker --check` checks configured model/key
presence, image/daemon access, required database tables, and artifact write access.
It does not authenticate a provider account or run an assessment/tool call.

### Display and design decisions

The five stages are **Waiting → Source review → Analysis → Report → Final checks**.
They represent confirmed workflow stages, not equal work units. No percentage or
finish-time estimate is invented from elapsed time or stage position.

The primary information is the current stage, then any attention notice, the stage
ledger, and the time/reference metadata. The existing paper/white surfaces,
forest-green navigation, Aptos/Segoe UI typography, quiet borders, and spacing are
retained. Amber indicates delay and red indicates interruption/failure. There is
no decorative progress animation or new UI library.

The stage list has semantic structure and a current-step indicator. Changes use
polite announcements. Times use localized formatting and tabular numerals. The
status-check control has visible focus and a 44px target; metadata and stages wrap
on narrow screens. Read-only users do not receive cancel/retry controls, and
cancellation requires confirmation. Terminal empty states do not imply analysis
is still running after completion/failure.

Customer messages explain the assessment state and next action without exposing
infrastructure instructions. Older stored diagnostics are translated when read,
not deleted. Findings remain qualified by evidence, scope, and coverage.

### Progress API contract

The authenticated scan-detail response adds these fields:

| Field | Meaning |
| --- | --- |
| `progress.stage` | `queued`, `source`, `analysis`, `report`, or `finalizing`. |
| `progress.health` | `healthy`, `waiting`, `delayed`, `interrupted`, `failed`, `cancelled`, or `completed`. |
| `progress.message` | Customer-safe explanation of the current state. |
| `progress.checked_at` | Time the server produced this snapshot. |
| `progress.last_update_at` | Most recent recorded assessment update. |
| `progress.last_activity_at` | Last substantive phase activity, distinct from monitoring notices. |
| `progress.last_signal_at` | Active lease heartbeat, when available. |
| `progress.deadline_at` | Active lease expiry, when available. |
| `progress.elapsed_seconds` | Elapsed assessment time; freezes for terminal states. |
| `progress.report_ready` | Whether a persisted report exists. |

Timestamps use UTC ISO strings and are displayed with `Intl.DateTimeFormat`.
Scan details also include top-level `created_at`; SSE events include `created_at`,
`sequence`, `kind`, and the safe summary.

### Update intervals and warning thresholds

| Mechanism | Interval/limit |
| --- | --- |
| Scan snapshot polling | 10 seconds, independent of SSE; overlapping refreshes are coalesced. |
| Capability refresh | 15 seconds. |
| Ordinary API request | 15-second timeout. |
| Silent SSE connection | Aborted after 45 seconds, then reconnects/replays. |
| SSE reconnection delay | Approximately 2 seconds. |
| Active worker/job heartbeat refresh | Approximately 10 seconds. |
| Worker readiness freshness | Approximately 30 seconds. |
| Per-job stale-heartbeat warning | Approximately 45 seconds. |
| Queue/no-new-phase warning | Approximately 2 minutes. |

Warning thresholds express uncertainty, not proof that a job failed. Liveness-only
messages do not hide stale analysis. Terminal scan states override stale health
warnings; a completed assessment cannot revert to running because a stream drops.

Independent polling means a connected SSE stream is not the only source of
status. Stream silence, API loss, and expired workspace access get visible
messages. Event replay uses the last sequence, fragmented CRLF frames are handled,
and duplicate or buffered events from an aborted subscription are ignored.
Out-of-order responses cannot replace the currently selected assessment.

## 5. Static lifecycle regression found and fixed

Publishing static phases required releasing the initial transaction/scan lock.
During analysis or report rendering, another process could fail a stale scan or
revoke its grant. The original worker could then overwrite that decision and
publish a successful result.

`run_local_static_scan` now reloads and locks the tenant-bound scan before each
resumed phase and before final publication. It verifies the expected state,
recorded backend, original source artifact/digest binding, and still-live grant.
Failed or revoked work cannot resume and publish findings/report rows.

The adapter also tolerates the stale-job reaper having already deleted that job's
workspace. Other cleanup errors still fail the run. The default
`commit_progress=False` behavior keeps the original caller-owned transaction;
only the process adapter opts into phase commits. Result rows remain atomic.

Three regression cases cover concurrent changes during analysis and reporting:

1. A scan reaped during analysis cannot resume or publish results.
2. A grant revoked after a phase commit prevents publication.
3. Reaping after report rendering, including actual workspace deletion, preserves
   the failed state and publishes neither findings nor a report.

The first two tests failed before the fix and passed afterward. A separate test
proves analysis progress is visible to another database session before the
scanner finishes, without prematurely exposing a report.

## 10. Monitoring and release boundaries

stream health. API/database failures cannot publish their own server events, so
the browser also detects connectivity loss. Cleanup and stale-job recovery need
the appropriate worker/reaper and execution service to be available.

an administrator health page, or a development preview route. The latter two
were suggested follow-ups, not implemented features.

assurance gates pass. Do not relax scope, authorization, artifact isolation,
network policy, evidence requirements, or cleanup to make a run appear successful.

operational monitoring remain separate release requirements. Never claim an
application is completely secure; report validated coverage and limitations.

deferred Burp issue alone unless a later task explicitly authorizes that work.
